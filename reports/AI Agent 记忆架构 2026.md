# 记忆赛道转向执行状态，FocalPoint 先拿证据

2026 年 AI Agent 记忆领域的主线变了。各家不再只拼"能回忆起多少对话事实"，开始比三件事：离线整合（consolidation/"dreaming"），把记忆当作长程任务的**执行状态**，以及对共享记忆的治理（溯源、权限、遗忘）。这个转向在方向上印证了 FocalPoint 的核心判断：结构化工作状态不同于对话记忆，确定性的 Spine 优于让 LLM 直接写存储。但 FocalPoint 原本以为空着的位置，现在已经有人占了。Beads（约 29k stars，有依赖图和 `bd ready`）、Claude Code 原生 Tasks、Backlog.md 和 Spec Kit 已经把"任务 DAG + MCP"做成了标配。README 里那张对比表拿 Mem0/Zep/Letta 作参照，比错了品类。代码层面，FocalPoint 的确定性内核测试扎实（690 个测试），但文档的范围远超代码。"三省审议"只记录调用方给的结论，GitHub/Notion 同步没有接进 MCP server，压缩只停留在规格里。`mcp` 依赖没有上限，全新安装后服务直接起不来。项目自己的 dogfooding 数据显示，高级工具从来没人用。项目自 2026-03-25 以后没有产品提交，已经休眠约 8 个月。我的结论是：**值得继续，但只能作为一个限定范围、带明确淘汰条件的实验，不能照原来的 FounderOS 蓝图往下铺。** 真正可辩护的差异化有三点：按 token 预算组装上下文，沿任务层级继承知识，从状态推导出确定性告警。下一步先修好安装，再用多会话恢复基准证明它比"一个 Markdown 文件 + Claude Tasks"更好。证明不了就收缩。

## 2026 年的进展：记忆从"召回"转向"整合与执行状态"

**专用记忆层已经收敛到少数头部玩家。** Mem0 约 69.5K stars，Apache-2.0。它在 2026 年 4 月发布新算法，自报 LoCoMo 从 71.4 升到 92.5、LongMemEval 从 67.8 升到 94.4，但 README 自己承认开源版涨幅更小 ([GitHub mem0ai/mem0](https://github.com/mem0ai/mem0))。Mem0 在 2025 年 10 月拿到 $24M 融资 ([TechCrunch](https://techcrunch.com/2025/10/28/mem0-raises-24m-from-yc-peak-xv-and-basis-set-to-build-the-memory-layer-for-ai-apps))。Zep 停掉了 Community Edition，开源精力集中到 Graphiti 时序知识图谱 ([Zep blog](https://blog.getzep.com/announcing-a-new-direction-for-zeps-open-source-strategy/))。Letta 在 2026 年 3 月把 Letta Code 定为旗舰，从记忆基础设施转向编码 agent 产品 ([Latent Space wiki](https://latent.space/wiki/letta-ai-558a42a5/))。Cognee 的 $7.5M 种子轮是唯一能明确定位在 2026 年的融资 ([Cognee blog](https://www.cognee.ai/blog/cognee-news/cognee-raises-seven-million-five-hundred-thousand-dollars-seed))。这些系统的存储单元全是"关于用户或实体的事实/片段"，没有一个存"带状态的工作项"。同时，Mem0 和 Zep 都推出了面向编码助手的 Agent Skills。资本正向 FocalPoint 的目标用户靠拢，走的是召回记忆路线，不是任务结构路线。

**前沿实验室把消费级记忆做成了免费标配。** Claude 记忆于 2026 年 3 月 2 日对免费用户开放，同时上线了从 ChatGPT/Gemini 导入的工具 ([MacRumors](https://macrumors.com/2026/03/02/anthropic-memory-import-tool/))。OpenAI 在 6 月发布 "Dreaming"，在后台整理记忆，并让记忆随时间更新，例如"计划去新加坡"会变成"去过新加坡"。OpenAI 自报事实召回从 67.9% 升到 82.8% ([OpenAI](https://openai.com/index/chatgpt-memory-dreaming))。开发者侧，Claude Code 形成了两层：人写的 CLAUDE.md（分 managed/user/project/local 作用域）和 Claude 自己写的 auto memory（MEMORY.md 加载前 200 行或 25KB）。文档明确说两者都是上下文，不是强制配置 ([Claude Code docs](https://code.claude.com/docs/en/memory))。对 FocalPoint 来说，这意味着它要打败的免费基线就是"维护良好的 MEMORY.md + 一个 TODO 文件"。

**学术界在 2026 年最显著的新方向，正好落在 FocalPoint 的生态位上。** 主流综述采用"形式 × 功能 × 动态"分类，并明确把 agent memory 与 RAG、context engineering 分开 ([arXiv 2512.13564](https://arxiv.org/html/2512.13564v2))。2026 年新起的分支有四条。第一条是 RL 训练的记忆管理器，代表是 Memory-R1 和 Mem-α ([arXiv 2508.19828](https://arxiv.org/html/2508.19828v5))。第二条是离线整合：Anthropic 11 月的文章把记忆拆成转录日志、模型笔记、wiki 式表示、注入上下文四层，用离线"dreaming"把各层连起来，报告 wiki + 搜索达到 61%、纯搜索 53%，每题省约 20k token ([Anthropic](https://www.anthropic.com/research/components-of-agent-memory))。第三条是**记忆即执行状态**：MAGE 主张记忆应追踪执行状态而非语义相似度，在 MemoryArena 上报告任务成功率提高 7.8–20.4 个百分点、token 减少 55.1% ([arXiv 2606.06090](https://arxiv.org/abs/2606.06090))。第四条是前瞻记忆与主动 agent。"Remember When It Matters" 让独立的记忆 agent 观察轨迹，并决定何时注入提醒，Terminal-Bench 2.0 从 37.6% 升到 45.9% ([arXiv 2607.08716](https://arxiv.org/html/2607.08716v1))。Pro-Memory 则指出，"记住正确的意图"不等于"在正确的时机行动" ([arXiv 2611.05731](https://arxiv.org/abs/2611.05731))。这些数字大多来自未经同行评审的预印本，研究笔记也没能打开 arXiv 原文核对，下文引用时按"方向性证据"对待。

## 简单存储赢下检索之争，评测体系却同时失信

**2026 年的证据总体有利于 FocalPoint 的"SQLite + FTS5，不用向量"选择，但有一个明确的软肋。** "Is Grep All You Need?" 在 116 道 LongMemEval 题上发现，结果直接返回到上下文时，grep 在所有 harness–模型组合上都胜过向量检索。不过结果改走文件、由程序化方式交付后，向量在 10 组里赢了 5 组。作者的结论是 harness 设计与检索方法同样重要 ([ar5iv 2605.15184](https://ar5iv.labs.arxiv.org/html/2605.15184))。Letta 的纯文件 + grep agent 在 LoCoMo 上拿到 74.0%，超过 Mem0g 自报最好的 68.5% ([Letta](https://www.letta.com/blog/benchmarking-ai-agent-memory))。确定性、保留溯源的 MGMem 在 LongMemEval-S 上 BM25 得 74.60%、混合检索得 73.80%，架构和 FocalPoint 非常接近 ([arXiv 2611.33174](https://arxiv.org/pdf/2611.33174))。更有分量的是 "Memory Tax"：许多专用记忆系统的表现**不如对原始历史做朴素 RAG**，损失来自摘要失真和信息不可达，给记忆补上原文出处能显著回血 ([arXiv 2610.34073](https://arxiv.org/abs/2610.34073))。软肋在于同义改写。Oracle 的厂商测试里，面对改写过的查询，grep 文件系统 agent 只有 29.7%，向量/DB agent 有 87.1% ([Lightspeed](https://lsvp.com/stories/file-systems-for-agents/))。另有研究指出，基准查询和答案共享实体词，这让 BM25 "轻松获胜" ([arXiv 2605.29630](https://arxiv.org/pdf/2605.29630))。

**同一时期，主流基准被系统性证伪。** 一次独立审计在六个常用基准里都找到了缺陷：LoCoMo 有错误归属的说话人、坏掉的证据指针，`evaluation.py` 里的 ROUGE-L 实际算的是 ROUGE-1；LongMemEval 有 15.2% 的时间戳早于其描述的对话 ([zxj0302 audit](https://github.com/zxj0302/agent-memory-benchmark-audit))。另一份审计认为 LoCoMo 有 6.4% 的标准答案是错的，理论上限只有 93.57% ([Penfield Labs](https://penfieldlabs.substack.com/p/we-audited-locomo-64-of-the-answer))。厂商数字之间互相冲突。Zep 在 LoCoMo 上的分数有 84、75.14、65.99、58.44 四个版本在流传，争议的 issue 最终因无人跟进而关闭 ([zep-papers#5](https://github.com/getzep/zep-papers/issues/5))。Mem0 自报 LongMemEval 94.4，一次独立复现只得到 49.0 ([opensourceaireview](https://opensourceaireview.com/blog/which-ai-memory-layer-has-the-best-published-benchmarks-in-2026))。

**这对 FocalPoint 是机会。** 在知识更新、遗忘、项目状态这类题上，确定性簿记本来就是强基线。有论文专门拿"冻结的最后写入解析器"做 MemoryAgentBench 冲突消解的对照 ([arXiv 2610.09193](https://arxiv.org/pdf/2610.09193))。NeurIPS 2026 的一篇论文发现，召回越多，过时事实越多，准确率反而下降，top-64 得 69%，top-512 只有 58% ([NeurIPS 2026](https://neurips.cc/virtual/2026/169567))。RealMem 是第一个以"动态更新项目状态"为题型的基准，作者结论是现有记忆系统"在管理长期项目状态上面临显著挑战" ([arXiv 2601.06966](https://arxiv.org/abs/2601.06966))。任务 DAG 回答"现在是什么状态"根本不需要检索。FocalPoint 的主场就在这里，而目前它在这类基准上没有任何数据。

## 任务 DAG 已成标配，真正的差异化只剩三处

**README 的对比表对它列出的五个竞品基本准确，但对真正的竞争者只字未提。** Mem0、Zep、Letta、CrewAI、Claude 记忆确实都没有任务生命周期、依赖 DAG 和心跳告警 ([README](https://github.com/jeff0052/focalpoint/blob/83553df/README.md))。FocalPoint 的直接竞品是 agent 原生的任务追踪器。Beads 自我定位为"编码 agent 的记忆系统"，有依赖图、`bd ready` 就绪工作查询、旧任务压缩和 `beads-mcp`。它改用 Dolt 存储，解决跨分支、跨 agent 的合并问题，在 2026 年 11 月进入 Thoughtworks 技术雷达 ([GitHub steveyegge/beads](https://github.com/steveyegge/beads)；[Thoughtworks Radar](https://www.thoughtworks.com/zh-cn/radar/tools/beads))。据二手资料，Claude Code 在 2026 年初把 todo 升级成支持依赖、可跨会话共享的 Tasks ([Dale Seo](https://daleseo.com/claude-code-tasks/))。Backlog.md 用 Markdown + MCP 提供里程碑、依赖和看板 ([GitHub MrLesk/Backlog.md](https://github.com/MrLesk/Backlog.md))，Spec Kit 用约 152k stars 的体量占住了"spec → plan → tasks"分解 ([GitHub spec-kit](https://github.com/github/spec-kit))。所以"FocalPoint 独有任务生命周期和 DAG"这句话在 2026 年 11 月已经不成立。角色人设可以被 BMAD 覆盖，定时检查可以被厂商的 scheduled tasks 覆盖。

**还站得住的差异化只剩三处，而且都需要证据。** 第一处是**按预算组装上下文**。`BundleAssembler` 组装 L0 仪表盘、告警层、L1 邻域（子节点、依赖、兄弟节点各有上限）和 L2 焦点，按角色过滤叙事类别，预算 8k/10k token，每次组装都写入 trace ([bundle.py](https://github.com/jeff0052/focalpoint/blob/83553df/fpms/spine/bundle.py#L24-L44))。在调研过的追踪器里，没有一个在交付上下文时做 token 预算。这一点直接回应了 context rot 问题。第二处是**沿任务层级继承知识**。子节点递归继承父链上的知识文档，并可以覆盖 ([knowledge.py](https://github.com/jeff0052/focalpoint/blob/83553df/fpms/spine/knowledge.py#L60-L88))。Beads、Claude Tasks、Backlog.md 都没有这个能力，研究笔记也没有找到专门做 DAG 知识继承的论文。第三处是**从状态推导出确定性告警**。心跳按截止时间、阻塞、停滞、收件箱积压给出五类告警，带 24h 去重和"防遗忘"重推 ([heartbeat.py](https://github.com/jeff0052/focalpoint/blob/83553df/fpms/spine/heartbeat.py#L1-L56))。OpenClaw 的心跳每 30 分钟读一份自由文本清单，每次都要调用模型 ([OpenClaw docs](https://docs.openclaw.ai/gateway/heartbeat))。FocalPoint 的告警每次检查零 LLM 调用，可以复现。

**有两个"卖点"其实是负资产。** "三省审议"对应的研究结论偏负面：同构多 agent 辩论在同等算力下通常打不过 self-consistency 或多数投票 ([arXiv 2310.01798](https://arxiv.org/pdf/2310.01798))。带来收益的是模型异构 ([arXiv 2502.08788](https://arxiv.org/abs/2502.08788))，而 FocalPoint 的实现里根本没有独立的评审调用（见下节）。另一个是"认知操作系统"的定位。它和 MemOS 撞名 ([GitHub MemTensor/MemOS](https://github.com/MemTensor/MemOS))，也让 Anthropic 那句话变得更刺耳："对强模型而言，让它们自己判断显著性比设定固定规则更有效" ([Anthropic](https://www.anthropic.com/research/components-of-agent-memory))。这句话直接挑战了固定的 L0/L1/L2 分层裁剪。把 L0/L1/L2 定位成"可被 agent 按需拉取的默认视图"，比定位成"替模型决定看什么"更经得起推敲。

## 代码体检：内核扎实，外壳多是承诺

**确定性内核是真东西。** `fpms/` 约 6.1k 行纯 Python/SQLite。schema 开了 WAL 和外键，有状态机、DAG 防环、XOR 约束、幂等命令表和审计 outbox ([schema.py](https://github.com/jeff0052/focalpoint/blob/83553df/fpms/spine/schema.py#L7-L97))。690 个测试里有 7 组不变量测试，在 `mcp<2` 环境下 9 秒跑完，以非 root 用户运行时全绿；以 root 运行时有 2 个失败，原因是 root 能在 `/nonexistent/path` 下创建目录 ([测试](https://github.com/jeff0052/focalpoint/blob/83553df/tests/invariants/test_invariant_atomic_commit.py#L126-L153))。"LLM 只发工具调用、绝不直接碰存储" ([README](https://github.com/jeff0052/focalpoint/blob/83553df/README.md)) 的设计，正是 2026 年治理类论文要求的"确定性状态所有者"。Governed Shared Memory 主张对跨 agent 传播做权限检查和时间上的替代关系管理 ([arXiv 2606.24535](https://arxiv.org/html/2606.24535v1))。SMSR 用写入时的 HMAC 溯源，把未签名注入的攻击成功率压到 0% ([arXiv 2606.12703](https://arxiv.org/abs/2606.12703v1))。这类防御放在一个独占写入权的 Spine 里最好实现。

**但几个招牌功能比文档描述的薄得多，作者需要正视。** "三省审议" `sansei_review` 只是一个结论记录器。评审结论由调用方 LLM 传入，不传时默认是 "No issues found" 和 "Feasible"，也就是默认通过。拒绝计数在批准后不会清零，整个过程没有并行执行，也没有独立的模型调用 ([__init__.py](https://github.com/jeff0052/focalpoint/blob/83553df/fpms/spine/__init__.py#L353-L422))。GitHub/Notion 适配器写好了，但生产代码里没有任何地方实例化它们。MCP server 只用三个路径构造 `SpineEngine`，所以 `sync_all()` 恒返回 0 ([mcp_server.py](https://github.com/jeff0052/focalpoint/blob/83553df/fpms/mcp_server.py#L35-L44))。`write_compressed()` 也没有调用方，`needs_compression` 从不被逻辑置位 ([narrative.py](https://github.com/jeff0052/focalpoint/blob/83553df/fpms/spine/narrative.py#L147-L160))。SYSTEM-CONFIG.md 不被任何代码解析，其中的预算（每类任务 100k–1M）和代码里的 8k/10k 互相矛盾 ([SYSTEM-CONFIG.md](https://github.com/jeff0052/focalpoint/blob/83553df/SYSTEM-CONFIG.md))。OVERVIEW 引用的 `FounderOS-Memory-Architecture-V1.md` 在仓库里不存在 ([OVERVIEW.md](https://github.com/jeff0052/focalpoint/blob/83553df/OVERVIEW.md))。

**有一个阻断级缺陷。** `pyproject.toml` 声明 `mcp[cli]>=1.2.0`，没有上限。mcp 2.x 把 `FastMCP` 改名为 `MCPServer`，于是全新 `pip install focalpoint` 解析到 2.x 后，server 一启动就报 `ModuleNotFoundError` ([pyproject.toml](https://github.com/jeff0052/focalpoint/blob/83553df/pyproject.toml)；[mcp_server.py#L23](https://github.com/jeff0052/focalpoint/blob/83553df/fpms/mcp_server.py#L23))。研究笔记没有核实 PyPI 上已发布的 0.4.0 wheel 是否也是这个依赖声明，但只要是，任何新用户的第一次体验就是崩溃。

**中文场景还有几处隐患，作为中文用户自己的工具尤其要紧。** FTS5 用的 `unicode61` 分词器切不开中日韩文本，CJK 查询无结果时只能退回 `LIKE` ([store.py](https://github.com/jeff0052/focalpoint/blob/83553df/fpms/spine/store.py#L473-L509))。token 按 `len(text)//4` 估算，而项目自己的配置写着中文约 2 token/字，中文叙事的预算会被低估好几倍 ([bundle.py](https://github.com/jeff0052/focalpoint/blob/83553df/fpms/spine/bundle.py#L594-L596))。数据库默认路径相对于当前工作目录，数据落在哪里取决于 MCP 客户端从哪个目录启动 ([mcp_server.py](https://github.com/jeff0052/focalpoint/blob/83553df/fpms/mcp_server.py#L39-L43))。心跳里的自动归档和 `sync_all` 里都有宽泛的 `except Exception: pass` ([__init__.py](https://github.com/jeff0052/focalpoint/blob/83553df/fpms/spine/__init__.py#L288-L300))。此外，打包元数据写的是 "Other/Proprietary License"，主页还指向旧仓库名 `founderOSclaudecode`，README 写 23 个工具，实际是 24 个。

**最关键的是项目自己的实证。** v0.4.0 在 48 个真实节点上自评 64/100 分："Recording Habits 4/10，89% 的 log 没有 category"，"Tool Utilization 2/10，workbench/三省/搜索从未使用"。作者自己的结论是"AI 不主动给 log 打 category"、"高级工具没人用" ([v0.4.0 milestone](https://github.com/jeff0052/focalpoint/blob/83553df/docs/milestones/2026-03-24-v040-analytics-and-research.md))。这和外部研究吻合：ATRBench 发现默认 agent 在主动性上比 oracle 低至少 62 分，靠提示词几乎补不回来 ([arXiv 2605.28108](https://arxiv.org/pdf/2605.28108))。Letta 也报告，编码能力强的模型不一定擅长写记忆和遵守记忆 ([Letta](https://www.letta.com/blog/evaluating-memory-in-production-agents/))。FocalPoint 的价值完全依赖宿主 LLM 自觉调用工具，而它自己的数据说明这件事不会自发发生。再加上 BSL 1.1 许可（非 OSI 认可，2030 年才转 Apache-2.0）([LICENSE](https://github.com/jeff0052/focalpoint/blob/83553df/LICENSE))、Mem0/Graphiti 都是 Apache-2.0、项目自述"还没用户" ([token-economy note](https://github.com/jeff0052/focalpoint/blob/83553df/docs/thinking/2026-03-25-token-economy-for-ai-agents.md))，以及 SQLite 单文件无法跨分支合并（Beads 正是为此迁到 Dolt），采用门槛相当高。

## 下一步：先证明"恢复工作"比 Markdown 快，再谈 OS

**值得继续的理由很具体。** 2026 年的研究把"记忆即执行状态"和"前瞻提醒"做成了显学，确定性存储和词法检索得到了 grep、Memory Tax、MGMem 等结果的支持，而按预算组装上下文、知识继承、状态告警这三项，在现有追踪器里确实没有对手。**收缩的理由同样具体。** 任务 DAG 本身已经商品化，平台方会继续吸收这块能力，项目自己的数据说明 agent 不会主动用它。代码在声明的功能和实际行为之间也有差距。因此正确的问题不是"FocalPoint 能否成为 AI 认知 OS"，而是"一个零 LLM 调用、带预算的工作状态层，能否让 agent 在上下文清空后更快、更准地恢复工作"。研究笔记提出的第三层评测方案正好可以回答这个问题。做法是把 SWE-bench-Verified 或 Terminal-Bench 任务切成 3–5 个会话，会话之间清空上下文，对比四种配置：无记忆、一个 Markdown 笔记文件、通过 MCP 接入 Mem0/Zep、接入 FocalPoint。指标包括任务成功率、恢复正确率（是否选对下一个 DAG 节点）、重复劳动率、token 消耗和耗时 ([研究笔记依据的先例：arXiv 2607.08716](https://arxiv.org/html/2607.08716v1))。还要报告竞品几乎都不报的写入侧指标：每次写入的 LLM 调用数（FocalPoint 为 0）、写入延迟，以及相同状态下组装出的上下文哈希是否一致。

下表按优先级给出建议，建议按顺序执行。每一级都以上一级的结果为前提。

| 优先级 | 时间 | 行动 | 为什么 / 通过标准 |
|---|---|---|---|
| **P0 止血** | 1–2 天 | 锁定 `mcp<2` 或迁移到 `MCPServer`。修正 License 元数据、仓库 URL 和 README 工具数。默认 DB 路径改到用户目录（如 `~/.focalpoint/`）。删掉或移出 `memory/` 里与项目无关的个人笔记 | 不做这些，任何评测或推广都无从谈起。通过标准：在干净的 venv 里 `pip install` 后 server 能启动 |
| **P1 决策门** | 2–4 周 | 搭建上表描述的多会话恢复基准，并加入 Beads 和 Claude Code Tasks 作为对照。同时补做 RealMem 的项目状态题和 MemoryAgentBench FactConsolidation（以 last-write 解析器为基线） | 这是整个项目的去留判据。**若对"Markdown 文件 + Claude Tasks"没有明确优势（例如恢复正确率或 token 没有显著改善），就停止独立开发**，把预算组装器和告警做成 Beads/Backlog.md 的插件 |

## 结论

这轮调研真正改变的判断是：FocalPoint 的问题不在方向，而在证据和入口。方向上，2026 年的学术和工业界都走向了"执行状态 + 确定性治理 + 离线整合"，这比 3 月写 ADR 时更有利于 FocalPoint。但"没有任何现有产品覆盖这个完整定位"这句话已经失去意义。用户不会为一个完整定位买单，只会为"清空上下文后能接着干活"买单，而 Claude Tasks 加一个 Markdown 文件已经免费提供了这项能力的七成。FocalPoint 的护城河只能是一个可测量的、确定性的增量：更少的 token、更准的恢复、零 LLM 成本的告警。

对作者个人而言，最划算的投入不是再写一份 PRD，而是花一周时间完成 P0 加上 P1 的最小版本。评测体系已经失信，大家都在争 LoCoMo 上几个百分点，这时一个公开 harness、带 grep 和 Markdown 基线、诚实报告输掉的题型的多会话任务基准，本身就有研究价值。即使 FocalPoint 最终输掉，这份基准也能留下来。
